# WP-01 authentication and private snippets

The website and VS Code use the same Supabase Auth account. Flask is the only
snippet data interface. VS Code exchanges the browser authorization code directly
with Supabase Auth. It talks to Flask for snippets and never connects to PostgreSQL.

## Architecture and limits

- Supabase Auth handles password hashing, signup validation and refresh tokens. Flask uses a rotating CSRF token and an opaque
  session handle in an HttpOnly, Secure, SameSite=Lax cookie. The session handle
  rotates on login. Supabase credentials stay in a private server-side PostgreSQL
  table, with a seven-day maximum web session and serialized refresh. Sign-out
  invalidates the local handle and requests provider revocation.
- VS Code Desktop and Insiders use the Supabase OAuth 2.1 server, a public client
  with S256 PKCE, a random state, and one registered HTTPS redirect URI.
  The browser bridge returns a short-lived code and state to the fixed extension
  ID `dineshkaarthik.snippo-code-snippets`. The extension accepts the matching callback once, within five minutes.
  The browser never receives the desktop access or refresh token. VS Code stores
  the tokens in SecretStorage and renews them as needed. Browser-only VS Code
  and remote extension-host authentication are outside WP-01.
- Flask validates every API bearer at the provider's OIDC UserInfo endpoint and
  checks the verified email, user, client ID and session ID before using the
  database. API requests use bearer credentials, while web forms use cookies
  and CSRF only. API `401` means authentication is absent, invalid or revoked,
  `404` covers missing and other users' IDs, `429` means rate limiting, and
  `503` indicates unavailable configuration, database or identity service.
  Successful snippet response shapes remain the same. Private responses use
  `Cache-Control: no-store`.
- VS Code sign-out clears local secrets and revokes that OAuth session ID for
  the Flask API, including when an access token is renewed. If offline, local
  sign-out still works and the extension reports that server revocation could
  not be confirmed. On the website, **Revoke all VS Code sessions** revokes
  the Supabase grant and its refresh tokens across devices. Provider JWTs may
  remain valid at services that only verify their signature until JWT expiry.
- The database role has owner-scoped SQL queries and RLS, with no direct
  Data API access for `anon`, `authenticated` or `service_role`. The Flask
  database credential is trusted server-side. Protect it, the session table,
  and any backups as credentials. Configure hosting access logs to redact
  OAuth callback query strings and authorization headers. Keep the publishable
  key only in Flask configuration. Never configure a service-role key.
- Supabase OAuth 2.1 Server is currently beta and available on the Free plan.
  The built-in SMTP generally sends only to project team members and allows two
  auth emails per hour. Use Mailpit locally and configure custom SMTP before
  testing with non-team addresses. Review the provider defaults and keep its
  abuse limits enabled in addition to the application's per-account and
  per-endpoint limits. Review OAuth beta restrictions and plan quotas before
  integration.

## Environment and isolated setup

1. Start an isolated Supabase instance with Auth and PostgreSQL. Install the
   Python dependencies with `python -m pip install -r requirements.txt`. Use
   `.env.example` for the Flask variable names. Set `SNIPPET_SESSION_KEY` to
   a random value of at least 32 characters, such as one produced by
   `python -c "import secrets; print(secrets.token_urlsafe(48))"`.
2. In the isolated database, make sure `public.snippets` exists with columns
   `sno integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`,
   `name text NOT NULL`, `cat text NOT NULL`, and `code text NOT NULL`.
   Apply `supabase/migrations/20261126000000_snippet_ownership.sql` as the
   migration administrator with `psql -X -v ON_ERROR_STOP=1`, then apply
   `supabase/migrations/20261126000100_default_starter_snippets.sql` in the
   same way. Provision the
   migration-created `snippet_app` role with a unique password using a secure
   administration session. In interactive `psql`, use `\password snippet_app`,
   then `ALTER ROLE snippet_app LOGIN`. Set `SNIPPET_DATABASE_URL` to
   that dedicated runtime login, with TLS certificate verification for hosted
   PostgreSQL. The app checks that both PostgreSQL session and current roles
   are `snippet_app`. The old `DATABASE_URL` is unused.
3. Apply the public-authentication migration after the ownership and starter
   migrations. For a fresh isolated environment, configure email confirmation
   and recovery using the templates in [Public authentication rollout](public-authentication.md).
   Keep refresh-token rotation enabled. On a local CLI stack set
   `auth.email.enable_confirmations` to `true` and use the local mail inbox.
4. Set the Supabase Auth Site URL to `SNIPPET_SITE_URL`. Enable the OAuth 2.1
   server, set the authorization path to `/oauth/consent`, and leave dynamic
   client registration off. Register a **public** client with no secret and one
   exact redirect URI: `<SNIPPET_SITE_URL>/oauth/vscode/callback`. Set
   `SNIPPET_VSCODE_CLIENT_ID` to that client's ID. Use a separate OAuth client
   and Supabase instance for local testing. Use the same site origin throughout.
5. Use HTTPS outside local development. For isolated loopback development only,
   set `SNIPPET_LOCAL_HTTP=1`, set the site origin to `http://127.0.0.1:5000`,
   and run `python main.py`. Configure the extension's user setting
   `snippetManager.serverUrl` to that same origin. The extension setting is
   application-scoped, so a workspace cannot supply a credential destination.

## Default starter snippets

New accounts created after the starter migration receive four owned Python
snippets after verifying their email address.
The database provisions them in the same transaction and records pending
accounts in a private table until confirmation. Existing accounts receive no
backfill. Deleting a starter is permanent unless the user creates it again.
Starter snippets appear in the ordinary web library and VS Code commands.

Test the signup and login path against isolated Supabase before a hosted
cutover. If the starter migration needs to be reversed, apply
`supabase/rollback_starter_snippets.sql` first, using the role that applied the
starter migration. It removes provisioning and clears pending entries while
preserving snippets that were already added.

## Legacy ownership and rollback

These steps are for a separately authorized integration window.

1. Take a protected schema/data backup, including sequence state, grants,
   and snippet data. Confirm restoration works in an isolated database. Record
   total legacy count and a checksum over ordered `sno, name, cat, code` rows
   internally. Put the legacy app/API behind a maintenance gate so concurrent
   anonymous traffic cannot change or read the data during the cutover.
2. Apply the versioned ownership and starter migrations in order with the
   migration administrator. It leaves
   historical columns and payloads intact. Every existing row starts with
   `owner_id IS NULL` and is hidden from the runtime role. Confirm the count
   and checksum match before bringing traffic back. Never run `migrate.py`
   during this cutover. The migration transaction can be rolled back on error.
3. Obtain written confirmation of each intended account and verify its UUID
   against `auth.users`. Prepare a private mapping of confirmed snippet IDs to
   account UUIDs. Never infer a mapping from sign-up order or email similarity.
   In an admin transaction, stage the confirmed IDs and UUIDs in a temporary
   table with a primary key on `sno`, then run the following. Check that the
   number updated equals the approved mapping count before committing.

   ```sql
   CREATE TEMP TABLE confirmed_owners (sno integer PRIMARY KEY, owner_id uuid NOT NULL) ON COMMIT DROP;
   -- Load the separately approved mapping into confirmed_owners here.
   UPDATE public.snippets AS snippet
   SET owner_id = mapping.owner_id
   FROM confirmed_owners AS mapping
   WHERE snippet.sno = mapping.sno AND snippet.owner_id IS NULL;
   ```

   Keep unmatched records unassigned. Verify assigned and unassigned counts,
   cross-account isolation, row content checksum and sequence behavior.
4. If an application rollback is needed, keep the maintenance gate in place and
   retain the migration and owner mapping. The unprotected legacy app must stay
   offline. If unwinding the database change before ownership is populated, an
   administrator can use `supabase/rollback_wp01.sql` after reversing the
   public-authentication and starter migrations (in that order). It refuses to remove
   ownership if any rows are assigned. Export and reconcile those assignments
   before considering a separate rollback. The rollback script leaves Data API
   roles revoked and RLS enabled. It drops only WP-01 support objects and the
   unpopulated ownership column, preserving all snippet records. Verify counts,
   checksum, and denied anonymous access again. Reconcile the migration ledger
   before reapplying a manually reversed migration.

## Verification and local VSIX

Run the backend suite against a **fresh, disposable loopback PostgreSQL
cluster** reachable in the default `postgres` database by a local admin. The
suite creates a separate fixture database and fixture roles, and uses a
synthetic Auth provider. Never set this variable to a shared cluster.

```sh
export SNIPPET_TEST_ADMIN_URL='postgresql://postgres@127.0.0.1:55437/postgres'
python -m unittest discover -s tests -v
cd vscode_extension
npm ci
npm test
npm run package -- --out ./snippo-code-snippets-1.0.0.vsix
```

The npm tests use mocked VS Code and HTTP endpoints. The VSIX includes compiled
extension code and no production npm dependencies. Check build-tool advisories
with `npm audit` and runtime dependency exposure with `npm audit --omit=dev`.
The new extension has its own SecretStorage. Disable or uninstall the old extension before installing Snippo and sign in again.
For a manual test install the VSIX with **Extensions: Install from VSIX** in a
clean desktop VS Code profile that satisfies the manifest's engine version.

- Register and verify two test accounts before signing in. Verify each receives four starter
  snippets. Register again using the same address and a different password,
  then verify that the original password still works. Sign out and confirm
  access to the snippet library requires signing in again.
- Use separate browser sessions to add snippets and search by name, code and
  category. Confirm neither account sees the other's categories or snippets.
  Check create/read/delete using both bearer identities. Verify cross-account
  IDs return 404 and an anonymous API request returns 401.
- Connect from VS Code, cancel or deny a sign-in, retry, and verify Show,
  Search, and Insert. Restart VS Code and verify persistence, then exercise
  access-token refresh and provider outage recovery. Sign out, and use the
  website to revoke all VS Code sessions. Confirm a device that was still
  signed in loses access.
- Before applying to a hosted environment, verify the intended Supabase Auth
  configuration, private runtime DSN, backup restoration, and absence of
  unplanned Vercel deployment. `feature/authentication` includes a
  branch-specific Vercel Git deployment opt-out.

### Automatic VS Code launch

Completing a fresh consent approval allows one automatic Stable VS Code launch
within 60 seconds. Flask ties that eligibility to the specific validated
callback and consumes it when the browser opens the callback. The page removes
the authorization query from browser history and uses a short-lived, opaque
marker with an origin-scoped browser lock to prevent duplicate launches in the
same browser profile.

Use **Open VS Code** or **Open VS Code Insiders** if the browser blocks the launch
or storage, or if Supabase completes authorization directly using an existing
grant. Decline uses the manual return link to deliver cancellation. If a
restored or reloaded page says the callback closed, restart sign-in from VS Code
if needed. Browser and operating-system protocol prompts still apply.
