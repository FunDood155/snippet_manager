## Design

1. Add `public.default_snippets` with integer sno primary key, name, cat, code. Seed the exact four existing defaults (Hello World / Basics, Loop Through a List / Loops, Function Template / Functions, Exception Handling / Error Handling) from `supabase/migrations/20261126000100_default_starter_snippets.sql` and live function. No fake Auth user or shared owner UUID. Admin can manage templates via Supabase Table Editor. Enable RLS and narrowly grant runtime `snippet_app` SELECT only, authenticated server context required; no anon/authenticated Data API or client write access. Keep existing personal RLS and FK untouched except the non-overlap constraint if needed. Do not expose private schemas.
2. Keep IDs unambiguous within existing nonnegative 32-bit API contract. Prefer reserved range for default IDs (e.g. 2,000,000,000–2,147,483,647) with database constraints/sequence bounds preventing collision with personal IDs; verify existing sequence/IDs first. Keep existing personal IDs unchanged. Use a constrained database identity/default sequence for shared rows, including admin inserts. Equivalent simpler enforced collision-free design acceptable; document rationale. Never reset personal sequence merely because IDs have gaps.
3. `store.py`: merge shared defaults and current owner's personal rows for listing/search/category filtering, and support single-snippet GET for shared IDs. Maintain existing API fields sno/name/cat/code and numeric IDs, routes, status codes and authentication. Keep personal creation, duplicate-name behavior and deletion owner-scoped; no shared row mutation through any app/API route. Ensure unverified/anonymous/revoked sessions see neither library. Use parameterized queries and RLS; avoid widening personal ownership predicates or grants. Website should clearly label shared defaults and omit their Delete controls; users can still insert/copy them. All four defaults are always shown (subject to filters); no per-user hide feature. Existing VS Code client should consume the same list unchanged.

Stop new per-user provisioning after additive migration/backend are live: retire the trigger `snippet_starter_accounts` on auth.users and its obsolete function/pending state and starter-only policy/grants as safely justified. Review dependencies including account deletion runbook, tests, migration ordering, RLS and auth registration/recovery. Keep pending table if operational compatibility requires it, but no new duplicate generation. No changes to auth confirmation, provider settings, sessions, login, OAuth, public package identity, or personal data isolation.
5. Delete only approved legacy and seed copies following preflight and safe cutover below. Preserve all user accounts and owned personal rows (especially 51). Document maintenance of defaults, current source of truth and cleanup/rollback steps; update account deletion runbook to reflect shared templates not belonging to accounts. Do not edit previously applied migrations; add new ordered migrations.
