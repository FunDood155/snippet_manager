# Account deletion runbook

This is a manual operator procedure for a verified, explicitly authorized deletion request. The website only provides support instructions. Run the procedure against isolated fixtures before using it in any environment.

1. Verify ownership over a trusted channel before confirming any account information. For example, resolve the already verified address through the private Auth dashboard and send an operator-initiated challenge to that address. Require a valid response and explicit consent to permanently delete the account and its owned snippets. Never ask for a password, sign-in or recovery link, authentication code, application token, or snippet contents. Stop if ownership or consent is uncertain.
2. Resolve the exact Auth UUID and confirm it matches the verified request. Privately record counts for that UUID in `public.snippets.owner_id` and the dependent tables below. Inspect current foreign keys, RLS, deployed routes and provider sessions against the expected schema. Shared templates in `public.default_snippets` have no account owner and are outside this procedure. After the hidden-defaults migration, the account foreign key cascades to its `snippet_private.hidden_default_snippets` preferences only. Include that table in the final dependent-row verification. Check for additional integrations or owned Storage objects. Supabase can reject deletion for Storage ownership. If resolving those objects would exceed the verified scope, stop. Keep identifiers and counts private, and keep token material, hashes and content out of work notes.
3. Block new access for the target. On the public-authentication build, an operator can add that exact UUID to `snippet_private.legacy_email_holds` using an idempotent insert and must commit the hold before proceeding. Verify that this gate is active on every deployment with access to the database. It blocks new web sessions and existing web/VS Code credentials at Snippo's authorization checks. It does not drain requests that already passed authorization or block Supabase email verification and its starter-snippet trigger. Use the supported Auth admin ban for the target while cleanup is in progress. If available in a trusted server session, revoke the user's Snippo OAuth grant and use global admin sign-out with the user's existing authenticated JWT. Revoke the grant first because global sign-out can remove the session needed for the grant call. Never request a JWT by email or expose a service-role key in an app. Verify the target's sessions and grant status privately. A ban alone leaves sessions active, and provider revocation does not invalidate every outstanding JWT immediately.
4. Quiesce in-flight target writes before removal, including any confirmation or recovery flow and starter provisioning. Clear the target's `web_sessions`, `email_flows` and `pending_starter_accounts` in the privileged database context using only exact UUID filters. Verify that verified access is blocked and the target's work has drained. If existing deployments, provider flows or concurrent requests cannot be safely contained and verified, stop before destructive work. The current app has no per-account drain mechanism or atomic transaction spanning Supabase Auth administration and Snippo cleanup. Waiting for token expiration alone is insufficient.
5. Using a privileged operator connection that can see the target's rows despite forced RLS, delete snippets with a bound UUID predicate (`WHERE owner_id = %s` in psycopg2). In the transaction, reconcile the affected count with the reviewed scope and confirm zero remaining target rows. Roll back if the scope differs. Keep the hold active. Delete the same UUID through Supabase Auth's server-side `auth.admin.deleteUser(uuid, false)` or the matching Dashboard Auth user action. Never delete by an email pattern, drop constraints or change a firewall rule. Unassigned legacy snippets and other accounts stay outside the operation.
6. Verify the Auth UUID no longer exists, its sessions and refresh tokens are gone, and the Snippo OAuth grant is absent or revoked. Check there are zero owned snippets and zero dependent rows for the UUID. If the operator-only WP-04 rollback archive still exists, check its `original_row->>'owner_id'` for the exact UUID and include any matching archived copies in the verified deletion scope. In the expected schema, the Auth delete cascades into `snippet_private.web_sessions`, `revoked_vscode_sessions`, `pending_starter_accounts`, `legacy_email_holds`, and `session_cutoffs` via `user_id`, and into `email_flows` via `owner_id`. `auth_limits` uses rate-limit buckets and has no owner FK. In an isolated rehearsal, also check that pre-deletion credentials fail on the website and VS Code API and refresh can no longer issue credentials. Verify actual provider behavior before recording completion. Provider-side JWTs can remain valid until expiration on surfaces that only check their signatures.

`public.snippets.owner_id` deliberately uses `ON DELETE RESTRICT`. If targeted snippet cleanup commits but the Auth deletion fails, keep the hold in place, record the partial state, and investigate the exact dependency or concurrent write. Recheck the same UUID, inspect and reconcile only its residual records, and retry the failed step with the existing verified consent. Do not mark the request complete until all checks pass. A failed verification or an unclear scope requires operator intervention.
