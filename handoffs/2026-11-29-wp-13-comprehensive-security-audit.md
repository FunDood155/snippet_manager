## Coverage — inspect every security-relevant component
Create a coverage matrix of actual tracked files, endpoints, database objects, extension entry points and deployment surfaces; classify each as inspected/tested/not applicable/blocked with rationale. Include:
1. **Architecture and trust boundaries:** browser/Flask, Jinja, Supabase Auth/Postgres, Vercel, extension and OAuth callback; identity flow, data classification, entry points and threat model. Anonymous, regular user, malicious account, expired/revoked session, compromised client and accidental misconfiguration. Document data flows and enforcement layers.
2. **Authentication and abuse:** registration, confirmation/recovery, Gmail SMTP integration (metadata only), login/logout, enumeration, rate limits/cooldowns, password policy, redirect validation, session fixation/rotation/expiry, cookie flags, CSRF, session revocation/cutoff, refresh concurrency, recovery token replay, failure behavior and free-tier abuse. Audit auth.py and public auth migrations; never test abuse against live endpoints.
3. **Authorization and isolation:** enumerate every web/API route and method in main.py and corresponding store.py access; ownership on list/detail/add/edit/duplicate/delete, search/filter/sort/pagination, favorites, hidden/shared defaults, recent usage, category management and template metadata. Check default read-only behavior, IDs, stale/mismatched sessions, legacy v1 and v2 API, mass assignment, IDOR/BOLA, CSRF and bearer/cookie separation. Verify user A/B and unauthenticated denial with synthetic fixtures; inspect database enforcement independently of app code.
4. **Database:** inspect all nine migration files plus rollback scripts, actual migration history, tables/columns, constraints, policies (including FORCE RLS where needed), grants including column and sequence permissions, roles/memberships and bypass/inheritance, transaction-local identity, SECURITY DEFINER/search_path, triggers/functions/views, exposed schemas/Data API/RPC, default privileges, owner/foreign-key/cascade integrity, legacy archive access, personal/shared ID ranges, hidden/favorites/recents, account deletion and backups/recovery limits. Compare desired vs live schema. Read-only aggregate checks, no personal code or identity dumps. Verify application role least privilege and two-user isolation on disposable PostgreSQL. Explain any differences in local vs live roles/config.
5. **Application and frontend:** SQL injection, parameterization, input validation and size limits, XSS (stored/reflected/DOM), template injection, syntax highlighting, escaping, copy/paste and placeholder rendering (literal/opt-in), malicious names/categories/languages/code, HTML/JSON/attribute contexts, JS fragment navigation/history/stale requests, open redirects, origin/Host/proxy trust, CSP and other headers, cache/no-store, error handling, debug modes, denial-of-service/resource limits, request timeouts, race conditions, safe logging. Inspect all templates, JS and relevant config. Confirm snippets are never executed by web app.
6. **VS Code extension:** inspect all TypeScript, manifest, activation/commands/menus/shortcuts, auth token SecretStorage, PKCE/state/callback URL handling, URI handlers, token refresh/revocation/logout, server URL trust/HTTPS and loopback, redirect handling, request headers/timeouts/response validation, account switches and concurrent requests, scope and consent for selected code upload, cancellation and duplicate/uncertain writes, recents, native placeholders escaping and no code execution, malicious remote metadata, private cache/logging, workspace trust/remote host behavior as applicable, packaging exclusions and extension identity/permissions. Review actual 1.1.1 package if accessible; distinguish source inspection from artifact and desktop testing. Never use real credentials in tests.
7. **Infrastructure and deployment:** vercel.json, Production vs Preview, environment separation, secret variable scopes/names, public endpoint exposure, headers, deployment protection, logs and retention, branch/deploy permissions, build/runtime settings and Tokyo region. Supabase auth redirect allowlists, registration settings, SMTP, public keys vs privileged keys, network restrictions and free-tier limitations. Record unavailable config; no settings edits or deployment. Verify current Production version and official Marketplace identity if accessible, without assuming user's installation state.
8. **Supply chain and repository:** Python requirements, npm manifest/lockfile (runtime vs dev/build dependencies), supported versions, known advisories via available current authoritative tools (pip-audit/npm audit or equivalent), transitive packages, lock consistency, package scripts, package provenance, release artifact contents, ignored files, env example, git history secret exposure indicators, repo visibility/access controls and branch protection metadata where authorized. Redact findings; never expose actual secrets. Distinguish confirmed exploitable vulnerabilities, advisory-only matches, dev-only issues and scanner false positives. Do not upgrade packages; feed exact findings to WP-15.
9. **Operational resilience/privacy:** outage and auth/provider failure paths, bounded retries, resource exhaustion, database connection handling, logging of sensitive code/tokens, retention/account deletion, backup/restore procedures and rollback safety, incident-response readiness, user-facing error handling and documentation claims. Inspect README, USER_GUIDE and docs for contradictions and risky instructions. Do not perform backup restore in live DB.

Use disposable DB with migrations and synthetic identities; never use production DB as fixture. Add temporary audit-only scripts outside committed source if needed.
